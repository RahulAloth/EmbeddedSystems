# ISO 26262 — Full Overview (Automotive Functional Safety)

ISO 26262 is the international standard for **functional safety of road vehicles**.  
It defines the processes, requirements, and safety lifecycle needed to ensure that automotive electronics do not cause unreasonable risk.

---

## 1. Introduction to ISO 26262

ISO 26262 applies to **electrical and electronic (E/E) systems** in passenger cars, trucks, buses, and motorcycles.  
It is derived from IEC 61508 but tailored for automotive.

Key goals:
- Prevent hazards caused by malfunctioning E/E systems.
- Ensure systematic and random hardware/software faults are controlled.
- Provide a structured safety lifecycle from concept → decommissioning.

---

## 2. ISO 26262 Structure (All Parts)

ISO 26262 consists of **12 parts**:

1. **Part 1 — Vocabulary**  
   Defines terminology used throughout the standard.

2. **Part 2 — Management of Functional Safety**  
   Safety culture, roles, responsibilities, planning, audits.

3. **Part 3 — Concept Phase**  
   Hazard analysis, risk assessment, ASIL determination.

4. **Part 4 — Product Development: System Level**  
   System architecture, safety goals, technical safety requirements.

5. **Part 5 — Product Development: Hardware Level**  
   Hardware safety requirements, metrics, FMEDA, fault coverage.

6. **Part 6 — Product Development: Software Level**  
   Software architecture, coding guidelines, verification, partitioning.

7. **Part 7 — Production, Operation, Service, Decommissioning**  
   Safety during manufacturing and lifetime operation.

8. **Part 8 — Supporting Processes**  
   Configuration management, change management, qualification of tools.

9. **Part 9 — ASIL‑Oriented and Safety‑Oriented Analyses**  
   FMEA, FTA, dependent failure analysis.

10. **Part 10 — Guidelines**  
    Clarifications and examples.

11. **Part 11 — Semiconductors**  
    Safety requirements for SoCs, MCUs, hardware IP.

12. **Part 12 — Motorcycles**  
    Safety lifecycle adapted for motorcycle systems.

---

## 3. ASIL Levels (Automotive Safety Integrity Levels)

ASIL defines the required safety rigor.

- **QM** — No safety requirement (Quality Management)
- **ASIL A** — Lowest safety requirement
- **ASIL B**
- **ASIL C**
- **ASIL D** — Highest safety requirement

ASIL is determined by:
- **Severity (S)**
- **Exposure (E)**
- **Controllability (C)**

---

## 4. Mandatory ISO 26262 Requirements (Core Safety Principles)

### 4.1 Freedom From Interference (FFI)
Mandatory for mixed‑criticality systems.

Must ensure:
- No **memory interference**
- No **timing interference**
- No **communication interference**

This is why AUTOSAR uses **memory + execution partitioning**.

---

### 4.2 Functional Safety Management
Organizations must:
- Define safety roles
- Maintain safety culture
- Perform audits and assessments
- Track safety anomalies

---

### 4.3 Hazard Analysis & Risk Assessment (HARA)
Mandatory steps:
- Identify hazards
- Determine severity, exposure, controllability
- Assign ASIL
- Define safety goals

---

### 4.4 Safety Lifecycle
ISO 26262 mandates a full lifecycle:
- Concept
- System development
- Hardware development
- Software development
- Production
- Operation
- Decommissioning

---

### 4.5 Hardware Safety Requirements
Mandatory:
- Fault metrics (SPFM, LFM)
- FMEDA
- Diagnostic coverage
- Safe state definition

---

### 4.6 Software Safety Requirements
Mandatory:
- Deterministic execution
- Memory protection
- Partitioning
- Defensive coding
- Verification & validation

---

### 4.7 Tool Qualification
Tools that can introduce safety risk must be qualified.

---

### 4.8 Safety Case
A structured argument proving the system is acceptably safe.

Mandatory for ASIL‑B/C/D.

---

## 5. Safety Mechanisms (Examples)

- Watchdog supervision  
- Redundant sensors  
- Plausibility checks  
- Memory protection (MPU/MMU)  
- Safe state fallback  
- CRC, counters, freshness checks  
- Diagnostic monitors

## 6. ISO 26262 and AUTOSAR

AUTOSAR implements ISO 26262 requirements through:
- OS‑Applications (software partitioning)
- MPU‑based memory isolation
- Deterministic scheduling
- E2E communication protection

## 8. Summary

ISO 26262 ensures that automotive E/E systems are developed with a rigorous safety process.  
Mandatory requirements such as **Freedom From Interference**, **ASIL independence**, **fault containment**, and **deterministic behavior** directly influence modern automotive architectures like AUTOSAR.

# ISO 26262 — Full Compliance Checklist (Engineering Reference)

This checklist covers all phases of the ISO 26262 functional safety lifecycle:
Concept → System → Hardware → Software → Production → Operation → Supporting Processes → Safety Case.

---

# 1. Management of Functional Safety (Part 2)

- [ ] Define safety culture and organizational responsibilities  
- [ ] Appoint safety manager and safety team  
- [ ] Create Functional Safety Plan  
- [ ] Establish confirmation measures (audit, assessment, review)  
- [ ] Define anomaly management process  
- [ ] Ensure competence management (training, qualification)  
- [ ] Maintain safety documentation repository  
- [ ] Ensure supplier safety capability and agreements  
- [ ] Define escalation paths for safety issues  

---

# 2. Concept Phase (Part 3)

## Hazard Analysis & Risk Assessment (HARA)
- [ ] Identify vehicle-level hazards  
- [ ] Determine severity (S), exposure (E), controllability (C)  
- [ ] Assign ASIL (QM, A, B, C, D)  
- [ ] Define safety goals  
- [ ] Document operational scenarios  
- [ ] Identify safe states  
- [ ] Define functional safety concept (FSC)  

---

# 3. System Development (Part 4)

- [ ] Derive technical safety requirements (TSRs)  
- [ ] Allocate TSRs to system elements (HW/SW)  
- [ ] Create system architecture with safety mechanisms  
- [ ] Perform system-level FMEA/FTA  
- [ ] Ensure Freedom From Interference (FFI)  
- [ ] Define system-level diagnostics  
- [ ] Define system integration & verification plan  
- [ ] Validate system safety concept  

---

# 4. Hardware Development (Part 5)

## Hardware Safety Requirements
- [ ] Derive hardware safety requirements from TSRs  
- [ ] Define hardware architecture  
- [ ] Identify safety mechanisms (lockstep, ECC, watchdog, monitors)

## Hardware Metrics
- [ ] Calculate SPFM (Single Point Fault Metric)  
- [ ] Calculate LFM (Latent Fault Metric)  
- [ ] Calculate PMHF (Probabilistic Metric for Random Hardware Failures)

## Analysis
- [ ] Perform FMEDA  
- [ ] Perform FTA  
- [ ] Perform dependent failure analysis (DFA)

## Verification
- [ ] Hardware integration testing  
- [ ] Hardware-software interface testing  
- [ ] Hardware safety validation  

---

# 5. Software Development (Part 6)

## Software Safety Requirements
- [ ] Derive software safety requirements from TSRs  
- [ ] Define software architecture  
- [ ] Ensure partitioning (memory, execution, communication)  
- [ ] Ensure deterministic behavior  
- [ ] Define error handling & safe state logic  

## Implementation
- [ ] Follow safety coding guidelines (MISRA, CERT)  
- [ ] Ensure defensive programming  
- [ ] Ensure memory protection (MPU/MMU)  
- [ ] Ensure timing protection (WCET analysis)  
- [ ] Ensure communication protection (E2E, CRC, counters)

## Verification
- [ ] Static analysis  
- [ ] Unit testing  
- [ ] Integration testing  
- [ ] Software qualification testing  
- [ ] Back-to-back testing (model vs code)  
- [ ] Coverage analysis (MC/DC for ASIL‑D)
